# KapiLab

Console local para inspecionar pacotes e comparar os contratos da IDE. O projeto fica fora da solução principal e não compõe Desktop, Benchmarks, DI global, LiteDB do usuário ou cofre.

## Build

O backend padrão segue `Directory.Build.props` (WinML no Windows e Cpu nos demais ambientes). Para restaurar, compilar e testar explicitamente:

```powershell
./scripts/lab/build_kapilab.ps1 -Backend Cpu -Test
./scripts/lab/build_kapilab.ps1 -Backend Cpu -Offline -Publish
./scripts/lab/build_kapilab.ps1 -Backend WinML -Offline -Publish
```

Os lockfiles do KapiLab são próprios por backend. A solução principal não restaura este console; o wrapper acima valida seus projetos. Em rede isolada, `-Offline` mantém restore locked e desativa apenas a auditoria online de vulnerabilidades do NuGet, indisponível sem acesso ao feed: `./scripts/lab/build_kapilab.ps1 -Backend Cpu -Offline -Test`. Em ambiente com rede, deixe `-Offline` desativado para manter essa auditoria.

Scripts de avaliação Python usam por padrão o apphost publicado listado em `tools/kapilab.lock.json`; antes de cada comando, o wrapper confere SHA-256 do apphost e hash determinístico de todos os arquivos publicados. O lock separa Cpu/WinML e registra RID, GenAI, runtime e commit/dirty. A publicação local atual é framework-dependent `win-x64`, exige .NET 10 instalado e fica em `artifacts/f7b/publish/` (ignorado pelo Git). Chamar `run(..., dotnet_executable=...)` opta explicitamente por desenvolvimento via `dotnet run --no-build`. Em ambas as rotas, o subprocesso não usa shell, tem timeout/workspace explícitos e ambiente filho allowlist; a única variável de aplicação permitida é `KAPILAB_MONGO_URI`, validada para `mongodb://` com host loopback explícito (sem SRV ou múltiplos hosts). O wrapper vincula o resumo JSON em stderr ao comando solicitado e exige que seu exit code coincida com o processo. A função `run(*args, expect=0, workspace=..., expected_backend=..., expected_genai=..., backend=...)` retorna `(returncode, stdout, summary)`; o preflight opcional consulta `env`. Códigos inesperados 6–9 viram exceções tipadas. Publicação Cuda, ARM64 e Linux ainda não estão habilitadas.

## Comandos disponíveis

```text
kapilab env [--expect-genai <versão>] [--expect-backend <backend>]
kapilab npu inventory
kapilab guidance smoke --package <diretório> --prompt-file <arquivo> --grammar-file <arquivo> [--device cpu|gpu] [--max-tokens 64]
kapilab model inspect (--package <diretório> | --models-dir <diretório>) [--hardware]
kapilab model validate (--package <diretório> | --models-dir <diretório>) [--hardware] [--strict-kapi] [--verify-hashes]
kapilab model run autocomplete --package <diretório> --in <records.jsonl> [--device auto|cpu|gpu|npu]
kapilab model run chat --package <diretório> --in <chat.jsonl> [--device auto|cpu|gpu|npu] [--context-tokens <n>] [--max-tokens 256] [--limit 100]
kapilab bench autocomplete --package <diretório> --in <records.jsonl> [--warmup 1] [--iterations 1] [--out <arquivo.jsonl>]
kapilab bench autocomplete --matrix <matrix.json> --in <records.jsonl> [--out <report.json>]
kapilab bench chat --package <diretório> --in <chat.jsonl> [--device auto|cpu|gpu|npu] [--context-tokens <n>] [--max-tokens 256] [--limit 100] [--warmup 1] [--iterations 1]
kapilab bench chat --matrix <matrix.json> --in <chat.jsonl> [--context-tokens <n>] [--out <report.json>]
kapilab contract render --in <records.jsonl> [--contract editor-context-v1|local-agent-fim-v0]
kapilab contract tokenize --package <diretório> --in <render.jsonl> [--context-tokens 2048] [--completion-tokens 32] [--out <tokens.jsonl>]
kapilab contract diff --expected <tokens.jsonl> --actual <tokens.jsonl> [--out <diff.json>]
kapilab parity compare --in <observations.json> [--tolerances <tolerances.json>] [--out <parity.json>]
kapilab catalog export --provider <id> --surface in-process|session-channel [--out <snapshot.json>]
kapilab catalog export-plan --provider <id> --in <synthetic-plan.json> [--out <snapshot.json>]
kapilab catalog check --expected <baseline.json> --actual <current.json>
kapilab catalog plans --in <plan-cases.json> [--out <plan-snapshot.json>]
kapilab catalog invoke --in <invocation-cases.json> [--out <report.json>]
kapilab agent replay --in <replay-cases.json> [--out <report.json>]
kapilab matrix run --in <process-matrix.json> [--out <report.json>]
kapilab report evaluate --gates <gates.json> --evidence <run-evidence.json> --out reports/lab/report.json
kapilab report merge <report.json> <report.json> [...] --out reports/lab/merged.json
kapilab --workspace <workspace> samples generate --seed <inteiro> [--count 100] [--index <índice>] [--out data/lab/samples.jsonl]
```

`samples generate` constrói apenas exemplos sintéticos a partir de seed e índice; não aceita arquivo/dataset de entrada,
não acessa MongoDB e não executa a consulta. Cada linha `kapilab-synthetic-samples-v1` informa `split=lab`,
`origin=synthetic` e `execution=skipped`. Comparadores numéricos e estágios são selecionados dos catálogos do editor;
o teste de diversidade com seed fixa cobre 400 casos e confere reprodutibilidade, operadores, estágios, campos, sintaxe
com `MongoCodeValidator` e classificação pelo parser/contexto/cursor da IDE. Essa validação cobre sintaxe/contexto local,
não compatibilidade semântica com um servidor MongoDB. `--index N --count 1` reproduz exatamente a linha N do lote com a
mesma seed. Lotes aceitam 1–10000 registros e no máximo 64 MiB; a escrita em arquivo é atômica e limitada a `data/lab`,
`reports/lab` ou `tmp`. Essas amostras não constituem dataset de treinamento.

O schema de amostras publicado aqui é local e versionado como `kapilab-synthetic-samples-v1`: a especificação externa
referenciada pela meta (§5.4) não está disponível neste checkout para verificar equivalência campo a campo.

`contract render` usa `AutocompleteContextBuilder` e `ModelPrefix` da IDE para `editor-context-v1`. A opção `local-agent-fim-v0` percorre `AgentContextProvider` e `LocalAgentProvider.RunTurnAsync` com um recorder que captura o `ModelGenerationRequest` real sem inferência; o output tem hashes e medidas, sem prompt/contexto bruto. Selecione explicitamente o laboratório por `--workspace` ou `KAPILAB_WORKSPACE`, inclusive quando a saída for stdout. JSONL vai para stdout por padrão; logs e resumo de execução ficam em stderr. Saídas em arquivo ficam limitadas a `data/lab`, `reports/lab` ou `tmp`. O comando recusa o conjunto cego, links/junctions no caminho de entrada/saída, conteúdo com marcador reservado e padrões conhecidos de segredo.

`contract tokenize` consome JSONL `kapilab-render-v1` e requer `--package` explícito. Valida o pacote pelo `LocalModelCatalog`, seleciona `IModelAdapter` por arquitetura/formato e usa seu `ITokenizer` e `ICompletionPromptBuilder`, os mesmos contratos escolhidos pelo runtime da IDE. O schema `kapilab-tokenized-contract-v2` registra somente hashes de prefixo/sufixo, identidade da família/formato, hashes de `genai_config.json`, `tokenizer.json`, `tokenizer_config.json` e, quando presente, do manifesto do adapter, contexto solicitado/efetivo, teto completion e IDs produzidos pelo adapter. O contexto efetivo usa a fórmula da IDE: mínimo entre orçamento solicitado e `max(64, janela efetiva do pacote - completion efetivo - overhead do prompt)`. Snapshots v1 antigos ainda podem ser lidos; novas comparações diferenciam versão e budgets. A API atual cria o tokenizer GenAI sobre `Model`; por isso o comando inicializa um `Model` com providers limpos e pode carregar/inicializar o decoder mesmo sem executar inferência. Pacote não suportado/incompatível falha; não existe fallback para tokenizer heurístico nem inferência de equivalência entre famílias.

`contract diff` compara snapshots tokenizados por `id`, texto original via hashes, família/formato, hashes dos arquivos de tokenizer/configuração e sequência exata de IDs. A ordem dos registros não importa; faltas, duplicatas, identidade inconsistente, texto diferente, IDs diferentes ou snapshots vazios não passam. Divergência retorna código 11. O diff não contém texto de prompt; registre a origem do orçamento em seus artefatos de rodada e não compare snapshots com budgets distintos como paridade equivalente.

`env` emite `kapilab-env-v2`, inclui o SHA-256 da assembly KapiLab carregada e registra commit/dirty da IDE quando encontra um checkout. Fora de um repositório Git, `ideCommit` e `ideDirty` são `null` (estado desconhecido), não um falso “limpo”. O hash da assembly não substitui o hash do apphost e do conteúdo publicado registrados pelo lock do wrapper.

`npu inventory` enumera os providers/dispositivos expostos pelo ONNX Runtime desta build, sem baixar pacotes ou carregar modelos. A ausência de NPU é resultado explícito com motivo e não transforma a indisponibilidade de CPU/GPU em falha do inventário.

`catalog plans` lê `kapilab-agent-plan-cases-v1` do workspace e avalia até 500 entradas por `AgentModePolicy.Plan`, a política pura usada pela IDE. O snapshot `kapilab-agent-plan-snapshot-v1` identifica `evidenceKind=synthetic-policy-input`, separa grants sintéticos de consentimento persistido e marca `toolInvocationPerformed=false`. A escrita opcional é atômica e não pode sobrescrever o input.

`catalog export --provider <id> --surface <in-process|session-channel>` compõe a registry registrada pela infraestrutura da IDE e exporta schemas/descritores como `kapilab-agent-catalog-v1`, `scope=provider-maximum`, `complete=false`. Usa LiteDB temporário, sem ler dados locais ou grants, e omite `approve`; não representa o plano de uma sessão autorizada. Na superfície in-process, schemas de entrada e saída são consultados por provider/tool e só são retornados quando a registry confirma a exposição correspondente.

`catalog export-plan --provider <id> --in <arquivo>` produz um snapshot distinto `kapilab-agent-catalog-plan-v1` para exatamente uma entrada `kapilab-agent-catalog-plan-input-v1`. `AgentModePolicy.Plan` avalia modo, permissões e fatos sintéticos; a exportação intersecta `ProductTools` somente com `GetInProcessDescriptors(providerId)`, preservando primeiro a fronteira de descoberta da registry. O snapshot marca `evidenceKind=synthetic-policy-input`, `synthetic=true`, `complete=false`, `toolInvocationPerformed=false` e `grantsVerified=false`; campos anotam estágio, categoria de confirmação, escopo de saída e hashes de schemas. Consentimento no input é somente fato de teste para a política, não autorização persistida nem grant efetivo. A superfície não lê repositório real de permissões, não invoca tools e não substitui `provider-maximum` ou o formato canônico externo.

`catalog invoke --in <arquivo> [--out <relatório>]` compõe `AddKapibaraStudioInfrastructure` com LiteDB temporário e provider fixture para executar até 500 casos por `IAgentRuntime` e pela registry real. A allowlist atual tem dois cenários: `list_connections` permitido pela política metadata-safe e `list_databases` negado sem grant (`PermissionMissing`) antes do handler/driver. A profile associada é sintética (`127.0.0.1:1`); o relatório contém status e decisão de auditoria correlacionados pelo turno, sem resultado bruto, e marca `grantsSupported=false` e `mongoDocumentsAccessed=false`. Um caso só corresponde se status e erro forem exatos e a auditoria terminal confirmar `Succeeded/PolicyAllowed` ou `Denied/PermissionMissing`; auditoria ausente ou divergente reprova o caso e o comando. Inputs fora da allowlist são recusados; não há concessão de grants nem leitura/escrita de documentos Mongo. Isso exercita somente a decisão atual sem grants e não cobre approval, grants positivos, expiração/revogação ou a matriz de referência externa.

Os testes do wrapper são executados com a biblioteca padrão do Python 3:

```powershell
python -m unittest discover -s scripts/lab/tests -v
```

A integração valida 200 casos sintéticos de plano contra o apphost publicado e confere schema, proveniência e bloqueios; não equivale a 200 chamadas reais da registry nem mede gates de produto. Outros testes de subprocesso cobrem `agent replay` e `catalog invoke`; as evidências e limites estão detalhados em `docs/phases/phase-07b-kapilab/evidencias-locais.md`.

`matrix run --in <arquivo> [--out <relatório>]` consome `kapilab-process-matrix-v1` e executa processos em sequência, sem shell, com `argv` separado, cwd no workspace, ambiente herdado filtrado por allowlist e timeouts. Executáveis relativos ficam confinados ao workspace; caminho absoluto requer declaração explícita de executável externo. O relatório é escrito atomicamente. Em fixture Windows, NTSTATUS de crash reconhecido retorna 10, exit comum diferente de zero retorna 1 e timeout/cancelamento/término não confirmado retorna 12, marca `complete=false` e preserva resultados anteriores. Essa fixture não prova crash real da IDE/provider.

As quatro rotas de inferência (`model run autocomplete/chat`, `bench autocomplete/chat`) aceitam `--via-queue` ou `--standalone-gpu` se o plano puder usar GPU; sem modo, a carga GPU falha antes da inicialização nativa. Os modos são mutuamente exclusivos. `--via-queue` exige `KAPILAB_GPU_TOKEN` não vazio e só verifica sua presença: o valor não é persistido nem ecoado. Essa opção não integra ou valida `gpu_queue.ps1`, fila/ledger, janelas, treino ou medição de carga. `bench --matrix` propaga o modo de coordenação a cada processo-filho, mas também não conecta à fila externa. `--standalone-gpu` aguarda a remoção de `tmp/gpu.pause` no workspace e aceita cancelamento.

Dentro do lease GPU, `tmp/kapilab.heartbeat` segue o schema `kapilab-gpu-heartbeat-v1` e é atualizado a cada 30 segundos. Guard exclusivo delimita ownership; encerramento normal remove o heartbeat, e a liberação do guard após crash permite recuperar/substituir o registro stale. Isso comprova somente a coordenação local do KapiLab: não houve inferência com pesos reais, nem validação da fila externa. Validação Linux é manual e permanece fora da meta executável deste chat.

`guidance smoke` requer arquivos UTF-8 de prompt e gramática Lark dentro do workspace (use `--workspace` ou `KAPILAB_WORKSPACE`). Arquivos são limitados a 8192 caracteres para prompt e 65536 para gramática, recusam BOM, links e o conjunto cego. O comando valida o pacote, usa o provider explicitamente selecionado e executa baseline e Lark guidance com o mesmo modelo, prompt tokenizado e limite de saída; o texto gerado nunca é decodificado nem emitido. A rota é identificada como `path=genai-direct`, não como caminho da IDE. A resposta `kapilab-guidance-smoke-v1` inclui `status`, suporte observado, tempos, tokens e `overhead_us_per_token`. `grammar_ok` fica `null`: este checkout não tem verificador independente de conformidade. Falha em `SetGuidance` retorna `status=not_supported` e código 1; geração guiada com zero tokens retorna `status=inconclusive` e código 1, pois não comprova suporte nem ausência dele. Falha nativa durante geração retorna código 5, preservando métricas baseline concluídas; cancelamento retorna código 12 e preserva medições completas. Pacote/provider não disponível produz `status=inconclusive`, `executed=false` e nenhuma medição. Os testes determinísticos validam apenas classificação/contrato; não são prova de smoke real. A aceitação real depende de pacote compatível instalado e execução explícita.

`model validate --strict-kapi` exige `kapibarastudio-model.json` com `schema: "kapilab-kapi-model-v1"` e `contextContract: "editor-context-v1"`. Este é um contrato **local do laboratório**, não o schema externo do exportador. O validador confere tipos, limites e relações de `capabilities`, `agent`, `reasoning`, `generation.agent`, `runtime.minimumGenAi` e SHA-256 do `chat_template.jinja` quando há raciocínio. `minimumGenAi` aceita uma versão semântica de três componentes; uma versão acima da incluída na IDE pode deixar `schemaValid=true` e `ideSupported=false`. O bloco `npu` e versões desconhecidas são recusados neste v1, pois a estrutura externa correspondente não está disponível no checkout. Campos não consumidos não recebem validação nem aprovação implícita.

`model validate --verify-hashes` exige `kapicoder_manifest.json` com `schema: "kapilab-kapicoder-manifest-v1"` e `files: [{"path":"caminho/relativo","sha256":"64 hex"}]`. Verifica, em streaming, **somente os arquivos listados** (`hashScope=manifest-listed-files`); o próprio manifesto não pode se listar. Caminhos absolutos, `..`, barras invertidas, duplicatas, links e junctions são recusados antes de abrir um arquivo referenciado. Sem manifesto ou com schema diferente, `hashesValid=false`; nenhum arquivo é baixado nem modelo carregado. O relatório `kapilab-model-validate-v1` mantém `schemaValid`, `hashesValid` e `ideSupported` separados; opção não pedida aparece ausente. Uma falha de qualquer validação solicitada ou da IDE retorna código 4. A verificação não afirma cobertura de arquivos omitidos nem equivalência com o manifesto externo ainda não versionado aqui.

`model run autocomplete` valida o pacote e então carrega explicitamente um único modelo pelo serviço ONNX e pelo provider de autocomplete da IDE. A entrada usa os mesmos registros FIM/completion do renderer, exige workspace explícito, recusa o conjunto cego e aplica os filtros de privacidade do produto. `--device` diferente de `auto` não permite fallback; o backend efetivo e a ocorrência de fallback automático são reportados. Inferência real CPU local está evidenciada em [evidências locais da Fase 7B](../../docs/phases/phase-07b-kapilab/evidencias-locais.md); GPU permanece sem prova.

Cada registro `kapilab-autocomplete-run-v2` inclui, por padrão, a sugestão já filtrada usada como ghost e seus caracteres/hash; a geração ocorre uma só vez pelo `AiAutocompleteProvider` compartilhado com o Desktop. A saída crua nunca é serializada por padrão. Para retê-la, `--keep-text` exige `--out` e aceita somente a entrada exata `Fixtures/autocomplete-raw-ghost-v1.jsonl` (SHA-256 `9edb16910cf7ed7d908ea2f53740cb364fae70b3d4a722000d4d0d3900dba40d`), escrita atomicamente sob `data/lab`, `reports/lab` ou `tmp`. O caminho de captura aplica o mesmo filtro do produto: se o resultado for recusado, o bruto não é exposto. Isso não valida overlay visual, decorador de latência da UI, GPU ou paridade Python.

`model run chat` aceita até 100 linhas JSONL independentes `{"schema":"kapilab-chat-input-v1","id":"turno-1","message":"Pergunta do usuário"}`. Só esses três campos são permitidos; `id` é ASCII limitado a 128 caracteres e `message` a 8192 caracteres. O comando valida todo o arquivo (até 2 MiB) antes de carregar o modelo, recusa IDs duplicados, segredos e marcadores reservados, e exige workspace explícito. Cada linha gera **uma rodada isolada** pela rota `ILocalAiModelService.StreamAsync(LocalModelRole.Chat)` com `ModelChatPrompt` e formatter Qwen3 reais, sem mensagem system fornecida pelo laboratório, tools, histórico, agente ou MongoDB. Qwen2/DeepSeek com capacidade `Chat` legada não possuem esse formatter e são recusados. A saída JSONL em stdout (`kapilab-chat-event-v1`) contém os chunks reais com texto e medições do chunk final; os chunks são retidos em memória até o filtro de privacidade aprovar a resposta inteira, evitando expor fragmentos de segredo antes da detecção. Não há arquivo de saída nem persistência da mensagem ou resposta. Erro/cancelamento emitem evento sem texto e os códigos 3/4/5/8/12 distinguem entrada/contexto, pacote, provider, privacidade e cancelamento.

`--context-tokens` é opcional em `model run chat`, `bench chat` e `bench chat --matrix`; quando ausente, usa a janela efetiva do pacote, limitada pelo máximo de `AutocompleteSettings`. Quando informado, deve estar entre 64 e o máximo absoluto da configuração; valor acima da janela do pacote é limitado à janela efetiva do modelo. `model run chat` inclui `contextWindowTokens` e `maximumCompletionTokens` nos eventos; o resumo do benchmark registra esses limites efetivos. Esse valor limita a janela entregue ao runtime via `AutocompleteSettings`, mas não comprova paridade com o orçamento calculado pelo tokenizador da IDE nem altera a tokenização da mensagem. `--max-tokens` continua entre 1 e 4096, e o runtime verifica o prompt tokenizado e a reserva de saída contra a janela do modelo. Falta executar sessão com pesos reais para confirmar template, tokenizer, provider, streaming e códigos no hardware alvo.

`bench autocomplete` carrega explicitamente um pacote e mede o provider real da IDE. As chamadas de `--warmup` usam o primeiro registro e ficam fora das estatísticas; cada registro é medido uma vez por `--iterations`. `kapilab-autocomplete-benchmark-sample-v3` inclui latência observada, TTFT e tokens/s reportados pelo runtime por amostra; o relatório `kapilab-autocomplete-benchmark-v5` e o resumo `kapilab-autocomplete-bench-summary-v5` registram as estatísticas, `complete`/`cancelled` e o motivo opcional. O resumo agrega tokens/s com contagem de medições/ausências, mínimo, média e percentis nearest-rank, além do tempo de carga do runtime e `processWorkingSetBytesAfterLoad` (working set do processo inteiro capturado após a carga, não memória exclusiva do modelo nem pico). Ctrl+C durante as amostras conserva medições concluídas, publica o relatório parcial incompleto e retorna código 12. Valores ausentes permanecem nulos; o texto sugerido não é persistido. Uma captura com completion incompleta é classificada `truncated`, `reason=incomplete`; isso não prova que o limite de tokens causou a truncagem. `--out` só aceita `data/lab`, `reports/lab` ou `tmp` no workspace. A execução exige pesos compatíveis e permanece manual; o foco F7B-09/11 passou 65/66 e as suítes completas Cpu/WinML passaram 255/258 cada. O smoke real CPU anterior usou schema v4 e não representa benchmark de corpus nem validação do schema atual v5.

`parity compare` consome um par local de observações `kapilab-parity-observations-v1`, sem executar modelos ou sintetizar tokens/logits. Tokenizer e prompt são comparados exatamente; prompt usa bytes UTF-8 em Base64 para preservar CRLF e escapes. Greedy e teacher exigem um arquivo local `kapilab-parity-tolerances-v1`; seus resultados são marcados `genai-direct`, não como rota IDE. O relatório `kapilab-parity-report-v1` retorna código 11 para divergência e código 6 para evidência inconclusiva e inclui hashes SHA-256 das observações/tolerâncias consumidas. Esses contratos locais habilitam comparação de observações reais, mas não substituem a referência Python nem provam paridade por si sós.

Exemplo mínimo de observação (dados sintéticos apenas para exercitar a CLI):

```json
{
  "schema": "kapilab-parity-observations-v1",
  "level": "tokenizer",
  "expected": { "schema": "kapilab-parity-observation-v1", "tokenIds": [10, 20, 30] },
  "actual": { "schema": "kapilab-parity-observation-v1", "tokenIds": [10, 20, 30] }
}
```

`bench chat` reutiliza a entrada e os limites de `model run chat`, incluindo `--context-tokens`, executa até 5 aquecimentos no primeiro registro fora das amostras e até 10 iterações medidas, com teto de 500 amostras. A variante `--matrix` propaga o limite a cada processo filho. Usa a mesma rota de streaming Qwen3; retém cada resposta somente em memória para verificar privacidade e emite no stdout **apenas métricas e categorias**, sem pergunta ou resposta. Cada amostra (`kapilab-chat-bench-sample-v1`) distingue `valid`, `null`, `refused` (recusa tipada do serviço), `failed` e `truncated` (`IsComplete=false`); o resumo (`kapilab-chat-bench-summary-v1`) inclui a contagem `ignored`, ainda não produzida por esta rota, além de `contextWindowTokens` e `maximumCompletionTokens` efetivos. Tempo observado de ponta a ponta e TTFT informado pelo runtime formam distribuições independentes via `LatencyStatistics`; TTFT ausente permanece nulo, sem substituição por zero. Cancelamento preserva as amostras já medidas no relatório parcial, devolve 12 e encerra a enumeração do runtime. Falha de provider/recusa retorna 5 e saída sensível filtrada retorna 8. Recusa expressa apenas no texto do modelo não é classificada como recusa, pois não há sinal tipado para isso. Não há `--out`, acesso a MongoDB, Python, agente, tools ou modelo externo. Sem pesos reais, resultados de sessão, latência e provider continuam não validados; F7B-13 permanece parcial.

`AgentToolCatalogSnapshot.Export(IAgentToolRegistry, providerId, surface)` extrai o máximo visível pelas APIs públicas de descritores/schemas (`in-process` ou `session-channel`) e produz `kapilab-agent-catalog-v1` com `scope=provider-maximum` e `complete=false`. Não consulta permissões salvas nem infere modo, plano, conexões ou grants. `approve` é omitida porque depende do plano ativo. O exporter aceita a instância da registry fornecida por um host; a chamada `catalog invoke` compõe a infraestrutura real separadamente, como descrito acima. Para in-process, os schemas de entrada e saída são consultados por provider/tool. A registry real retorna schema de saída somente após confirmar que a ferramenta está exposta àquele provider; o schema recebe identidade/versionamento e seu hash entra no snapshot. Implementações antigas da interface mantêm retorno nulo por padrão. O snapshot segue `complete=false` porque representa o máximo do provider, não modo/plano/grants.

`AgentToolCatalogPlanSnapshot.Export` é outra superfície: aceita um único `PlanInput` sintético validado, exige que o provider do caso seja igual ao provider solicitado, executa a política pura e intersecta a lista de `ProductTools` com `GetInProcessDescriptors(providerId)`. Nunca começa pelo catálogo global, nunca inclui tool apenas por estar no plano e nunca amplia exposição da registry. Hashes de schema são SHA-256 UTF-8; `snapshotSha256` cobre o conteúdo serializado sem o próprio hash. O output sempre declara entrada sintética, nenhuma invocação e grants não verificados. Isso não prova a autorização de um turno real e não é comparável ao snapshot `provider-maximum` pelo `catalog check` atual.

`catalog check` compara dois snapshots versionados lidos dentro do workspace selecionado, recusa links e o conjunto cego e retorna código 7 para mudança de catálogo/schema ou schemas ausentes. Mesmo sem drift, o resultado continua explicitamente `complete=false`; a comparação não valida grants nem prova que um plano de turno está autorizado.

`report evaluate` consome `kapilab-gates-v1` (JSON derivado/versionado pelo pipeline externo, com `version`, `source_hash` e `gates` contendo `id`, `owner`, `required`, `metric_id`, `operator` e `threshold`) e evidências locais v1/v2/v3/v4 (identidade de build/pacote/backend/provider, qualificação e métricas). v2/v3/v4 permitem declarar `status=skipped` ou `inconclusive`, sem converter isso em sucesso; v3 adiciona hash SHA-256 do artefato por métrica. v4 mantém `evidence_ref` como caminho relativo do artefato e adiciona `evidence_pointer` separado, interpretado como JSON Pointer RFC 6901. Para v4, o avaliador lê o artefato dentro do limite, calcula o hash e resolve o ponteiro sobre os mesmos bytes; só aceita o gate quando o alvo é número finito e exatamente igual ao valor declarado. Fragmento ausente/inválido, JSON inválido/duplicado, alvo ausente ou valor divergente não aprova. Relatórios v1-v3 mantêm o contrato anterior (`kapilab-report-v3`); evidência v4 produz `kapilab-report-v4`, aceito por `report merge` sob as mesmas verificações de identidade, definições, completude e hashes. Esses contratos são locais e não reivindicam equivalência ao schema externo. O comando não lê YAML nem cria gates. Referências e ponteiros são representados no relatório por hashes, sem copiar caminhos/texto potencialmente sensíveis. Entradas devem estar dentro do workspace e fora do conjunto cego; a CLI limita cada arquivo de configuração a 4 MiB. A saída exige `reports/lab`, `data/lab` ou `tmp`.

O contrato completo e um exemplo estão em [evidence-artifacts-v4.md](evidence-artifacts-v4.md); v3 permanece documentado separadamente em [evidence-artifacts-v3.md](evidence-artifacts-v3.md).

Ausência de gates, métrica, valor ou referência; execução/métrica desqualificada; falha em gate obrigatório; ou artefato incompleto gera resultado não aprovado e código 6. Uma falha em gate opcional fica registrada, mas não reprova gates obrigatórios aprovados. O relatório preserva versão/hash do conjunto de gates e identidade da execução. O avaliador verifica presença/proveniência declarada no artefato, mas não valida os arquivos apontados pelas referências nem substitui avaliadores externos (por exemplo, Exec Match/task success); esses resultados precisam ser exportados pelo dono como evidência versionada.

`report merge` exige pelo menos dois relatórios locais `kapilab-report-v2`/`kapilab-report-v3`/`kapilab-report-v4` dentro do workspace. Rejeita ausência de proveniência, IDs duplicados, diferenças de build/pacote/backend/provider, gate set ou definições/owners; ordena membros por `runId` e preserva cada relatório e gate sem sintetizar métricas. A CLI limita a 1000 entradas, 4 MiB por arquivo e 16 Mi caracteres após decodificação no total; conta texto em streaming antes de carregar o lote, decodifica UTF-8 estritamente nas duas passagens e limita cada leitura materializada ao orçamento restante. A agregação só passa quando todos os membros são qualificados, completos e aprovados; membro skipped/inconclusive não pode passar, e mistura de skipped com outro resultado fica `inconclusive` no resumo (o resultado individual é mantido). A saída usa `kapilab-merged-report-v1`, contrato local restrito, não a implementação completa do schema externo §5.11/§9.4. Os arquivos devem ficar dentro do workspace e não podem sobrescrever nenhuma entrada.
